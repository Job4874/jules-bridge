## Flask (flask + flask-cors)

### Configuration

- App created in `bridge.py` line 66: `app = Flask(__name__)`

- CORS enabled globally: `CORS(app)` — no origin restrictions (runs locally)

- No authentication middleware — local-only, firewall-protected

- Runs on port **5000** by default

### Error Handling Chain

All route handlers MUST use the `@route_errors` decorator (bridge.py lines 92–134). The decorator maps exceptions to HTTP status codes in this priority:

1. `BridgeHTTPError` → custom status code

2. `subprocess.TimeoutExpired` → 504

3. `ShellNotAvailableError` / `UnsupportedShellError` → 400

4. `IsADirectoryError` / `NotADirectoryError` → 400

5. `FileNotFoundError` → 404

6. `PermissionError` → 403

7. `re.error` → 400

8. `ValueError` → 400

9. `OSError` (EACCES/EPERM) → 403, (ENOENT) → 404, (other) → 500

10. All other exceptions → 500

### Request Parsing Pattern

Always use the bridge.py field helpers, never parse `request.json` directly:

```python
data = json_payload()                          # validates Content-Type + JSON
path = path_field(data)                        # string + control-char safe
name = string_field(data, "name")              # required string
opt  = string_field(data, "key", default="")   # optional with default
n    = int_field(data, "lines", default=50)    # optional int with default
content = content_field(data)                  # accepts "content" or "data" key

```

### Response Pattern

Always return `jsonify(dict(result))` where `result` is a typed dict/dataclass from a module. Never construct response dicts inline in route handlers.

## VM/browser model loop

Used by `modules/chat_service.py` and by non-stub `modules/reasoning_module.py`
calls for H-module and L-module model work. The bridge does not call provider
chat APIs directly.

### Configuration

- **Env var optional**: `BROWSER_MODEL_LOOP_URL` points VM workers at the local
  browser-loop service when that service is available.

- **No provider SDK dependency**: do not add direct provider clients to the
  bridge for chat or reasoning. Keep browser-loop integration behind
  `chat_service.chat(...)`.

### Model Alias System

Never pass raw model strings to reasoning routes. Use aliases:

```python
# In route body:
{"problem": "...", "model": "fast"}     # VM/browser model loop
{"problem": "...", "model": "smart"}    # VM/browser model loop
{"problem": "...", "model": "stub"}     # deterministic stub (unit tests, offline)

```

Alias mapping lives in `_MODEL_ALIASES` at the top of `reasoning_module.py`.
`fast` and `smart` intentionally point at the same loop boundary so call sites
do not depend on provider names.

### Fallback Behavior

If the VM/browser loop fails, times out, or returns non-JSON for a structured
reasoning call, the module silently falls back to stub output and logs a
`WARNING` to `jules_bridge.reasoning`. It does NOT raise. This is intentional
because the bridge must never crash due to model-loop failure.

### Usage Pattern

```python
# Direct module call (for testing):
from modules.reasoning_module import plan_only
result = plan_only("My problem", context="", model="fast")

# Via bridge route:
POST /reasoning/solve
{"problem": "My problem", "model": "fast"}

# Plan-only (H module, no execution):
POST /reasoning/plan
{"problem": "My problem", "model": "smart"}

```

### Rules

- Use `model="stub"` in unit tests unless explicitly patching
  `modules.reasoning_module._model_loop_chat`.

- Do not make provider API key presence a health signal. `/health/deep` should
  report `model_loop` readiness instead.

- When a user asks `/chat` to analyze the local codebase/repo, `chat_service`
  attaches a compact `LOCAL_CODEBASE_ANALYSIS_JSON` block generated by
  `modules.codebase_analyzer.analyze_codebase(...)`. This keeps the VM worker
  from answering from its isolated `/home/jules` checkout when the user means
  the Windows bridge repo.

## Cloud Sync

Used by `modules/cloud_sync.py`, the protected `GET /sync/status` route, and
the compact `cloud_sync` block in `/dashboard/status`. The protected
`POST /sync/publish-packet` route uses the same module for operator-reviewed
publish packets.

### Usage

```python
from modules.cloud_sync import get_cloud_sync_status

result = get_cloud_sync_status(timeout_s=4)

from modules.cloud_sync import build_cloud_publish_packet

packet = build_cloud_publish_packet(write_packet=True)
```

### Rules

- Status collection is read-only. Do not run `git push`, `git fetch`,
  `git pull`, `git add`, or `git commit` from dashboard polling.
- Return branch/upstream, ahead/behind, dirty counts, GitHub auth readiness,
  blockers, and warnings.
- Treat `dirty_worktree` as a cloud-publish blocker until the operator
  intentionally stages and commits the desired files.
- `build_cloud_publish_packet(...)` may write markdown/JSON review artifacts
  under `jules_inbox/cloud_sync/`, but it must never stage, commit, fetch,
  pull, or push.
- Publish packets classify dirty files into families, exclude generated/noisy
  files from generated `git add -- ...` commands, and emit review/test/commit
  commands for the operator to run intentionally.
- Never return raw remote URLs, token text, workspace paths, or commit subjects
  in dashboard snapshots.

### Rules

  the worktree is dirty.

## Gemini CLI (`@google/gemini-cli`)

Used by `modules/gemini_cli.py` and the protected `/gemini/*` bridge routes.
This is a terminal-agent integration, not a provider SDK dependency for
`chat_service` or `reasoning_module`.

### Install

```powershell
npm install -g @google/gemini-cli
```

The local Windows npm prefix is usually `C:\Users\abdul\.npm-packages`.
Prefer invoking the package `bundle/gemini.js` with `node` or using
`gemini.cmd`; avoid depending on the PowerShell-only `gemini.ps1` shim from
inside Python subprocesses.

### Bridge Usage

```text
POST /gemini/preflight
POST /gemini/prompt
```

- `/gemini/preflight` checks install readiness with `gemini --version` and
  local capability commands. Authenticated model execution is only checked when
  `run_smoke=true`.
- `/gemini/prompt` wraps `gemini -p` and defaults to `dry_run=true` plus
  `approval_mode="plan"`.
- `GEMINI_CLI_PATH` may point at a custom CLI path. `GEMINI_MODEL` is optional
  and only used when the caller does not provide a route-level model.
- Do not return or log API key values. Auth state can be reported as booleans
  or `likely_blocker` strings.

## Antigravity CLI (`agy`)

Used by `modules/antigravity_cli.py` and the protected
`/gemini/antigravity/*` bridge routes. This is the supported Google terminal
agent path for individual Gemini CLI migration, not a provider SDK dependency.

### Install

```powershell
irm https://antigravity.google/cli/install.ps1 | iex
```

The Windows installer places `agy.exe` under
`C:\Users\abdul\AppData\Local\agy\bin\agy.exe` and updates the user PATH
registry. Existing bridge/terminal processes may still need direct path
resolution until they restart.

### Bridge Usage

```text
POST /gemini/antigravity/preflight
POST /gemini/antigravity/prompt
```

- `/gemini/antigravity/preflight` checks `agy --version`, `agy models`,
  `agy plugin list`, and optional model execution with `agy -p`.
- `/gemini/antigravity/prompt` wraps `agy -p`, defaults to `dry_run=true`, and
  redacts prompt text from command previews.
- `ANTIGRAVITY_CLI_PATH` or `AGY_CLI_PATH` may point at a custom binary path.
  `ANTIGRAVITY_MODEL` is optional.
- Do not use `--dangerously-skip-permissions` in bridge-managed prompts.
- A passing Antigravity smoke proves the supported Google terminal-agent path,
  but it does not make legacy Gemini CLI `UNSUPPORTED_CLIENT` model execution
  pass. Keep both proof gates visible and report legacy Gemini as a caveat.

## Collaboration Proof

Used by `modules/collaboration_proof.py` and protected route
`POST /proof/collaboration`.

### Bridge Usage

```text
POST /proof/collaboration
```

- Default mode is side-effect safe: it checks current files, persisted evidence,
  local skill metadata, AKC readiness, HRM reasoning, and CLI/API preflights
  without launching workers or editing files.
- `include_live_checks=true` enables read-only live preflight checks such as
  Jules source readiness.
- `run_gemini_smoke=true` attempts authenticated Gemini headless model
  execution and supported Antigravity `agy -p` model execution. Legacy Gemini
  can legitimately block on Google auth/tier state while Antigravity passes;
  that legacy lane should not block completion when the supported `agy` lane
  proves model execution.
- `requirement_audit` maps the broad objective to evidence-backed rows; use this
  before claiming the active goal is complete.
- `completion_assessment.safe_to_mark_goal_complete` must be true before
  marking the active proof goal complete.
- Proof JSON is written to `jules_inbox/proof/COLLABORATION_PROOF.json` unless
  `write_state=false` or `state_path` is provided.

## Alliance Switchboard

Used by `modules/alliance_switchboard.py` and protected route
`POST /alliance/switchboard`.

### Bridge Usage

```text
POST /alliance/switchboard
```

- `objective` is required. `target_files` can bound the codebase scope.
- Defaults: `preferred_creator="jules"`,
  `preferred_implementer="antigravity_cli"`, and `complexity="complex"`.
- `include_live_checks=true` runs bounded Jules/Gemini/Antigravity preflights
  without launching Jules sessions or editing files.
- `run_implementer_smoke=true` optionally runs the small Antigravity model

  `ALLIANCE_IMPLEMENTER_GOOGLE_TERMINAL.md`,
  `ALLIANCE_SWITCHING_POLICY.md`, and `ALLIANCE_SWITCHBOARD_STATE.json` under

- Treat switchboard packets as role handoffs only. Live work still requires
  explicit calls to `/jules/*` or `/gemini/antigravity/*` with their own live
  flags.

## subprocess (via shell_executor)

### Configuration

- Wrapped by `modules/shell_executor.py` — never use `subprocess` directly in route handlers

- Three supported shells: `powershell`, `cmd`, `bash`

- Default timeout: **30 seconds** — pass `timeout=120` for long builds

### PowerShell Invocation

Always use `["powershell", "-Command", cmd]`, never `["pwsh", ...]`. The executor handles this internally:

```python
modules.execute(command="Get-Process", shell="powershell", timeout=30)

```

### Bash on Windows

The executor searches these paths in order:

1. `C:\Program Files\Git\bin\bash.exe`

2. `C:\Program Files (x86)\Git\bin\bash.exe`

3. `C:\Program Files\Git\usr\bin\bash.exe`

### Output Encoding

All subprocess output is coerced to UTF-8 via `_coerce_text()`: bytes → `decode("utf-8", errors="replace")`.
`modules.jules_orchestrator._run_cli_command()` also sets `encoding="utf-8"` and
`errors="replace"` on text pipes so `jules new` can receive packet prompts with
emoji/non-ASCII text on Windows.

### Return Contract

```python
ShellResult(exit_code=0, stdout="...", stderr="...", shell="powershell")

```

- `exit_code=0` does NOT guarantee success on Windows — always check stdout/stderr content too

## pyngrok

### Configuration

- Used ONLY in `start.py` — never in bridge.py or modules

- Fixed ngrok domain: `parade-marrow-pulp.ngrok-free.dev`

- Connects to local port 5000: `ngrok.connect(5000, domain=NGROK_DOMAIN)`

- Auth token: stored in ngrok's own config, not in `.env`

### Startup Sequence (start.py)

1. Launch `bridge.py` as subprocess

2. Poll `http://127.0.0.1:5000/ping` for up to 10 seconds (20 × 0.5s)

3. Open ngrok tunnel to port 5000 with fixed domain

4. If ngrok fails but local bridge is UP → warn but continue (local-only mode)

5. Keep-alive loop: check subprocess health every 2 seconds

### Rules

- Never import pyngrok in bridge.py or any module

- If ngrok tunnel fails, the bridge still works on localhost — this is intentional

- The ngrok URL is logged to console and bridge.log — agents can read it from there

## logging (stdlib)

### Configuration

- `RotatingFileHandler` writing to `bridge.log` at project root

- Max size: 10 MB, 3 backup files, UTF-8 encoding

- Format: `2025-06-25T14:30:00+0000 INFO jules_bridge: message`

- Both file and stdout handlers are tagged with `_jules_bridge_handler = True` to prevent duplicate registration

### Rules

- Always use `LOGGER = logging.getLogger("jules_bridge")` — never use `print()` for operational output

- The retrospective module reads `bridge.log` for pattern analysis — if you break the log format, you break retrospective analysis

- `start.py` has its own logger: `jules_bridge_start` — separate from the main bridge logger
